## 一、前端 vitest / eslint 从未在本机跑过（配置与用例已写好）

**现状**：`vitest.config.ts`、2 个 spec（`src/utils/__tests__/*.spec.ts`）、`.eslintrc.cjs`、`.prettierrc.json`
与 npm scripts 都已提交；依赖声明在 `package.json` 里，但本机 npm registry 不可达、缓存也没有这些包
（`npm install --offline --dry-run` 报 `ENOTCACHED`），所以**从未在 vitest / eslint 下实际运行过**。

已做的替代验证：`npm run test:offline`（`scripts/vitest-shim.mjs` + `spec-loader.mjs`）用零依赖方式
跑**同一批 spec**，实测 17 条断言通过——断言逻辑是验证过的，未验证的只是 vitest 这层框架接线。

**具体怎么做**（在有网络的机器上）：

```bash
cd fact-check-web
npm i                 # 会装上 vitest / eslint / prettier 等 6 个 devDependencies

npm run test:run      # 期望：2 个测试文件、17 条断言全通过
npm run lint          # 期望：无 error（可能有少量 warning 来自既有代码）
npm run format:check  # 期望：列出未按 prettier 格式化的文件（首次通常会有一批）
npm run format        # 想统一风格时执行，然后单独提交一次格式化改动
```

**可能的坑**：

1. `npm i` 会同时更新 `package-lock.json`——**这是预期的**，请把 lockfile 一起提交。
2. `npm run lint` 若报配置相关错误（例如 `@typescript-eslint` 版本与 eslint 9 的 flat config 不兼容）：
   当前配置用的是 eslint 8 的传统 `.eslintrc.cjs`。要么保持 eslint 8（推荐，配置已就位），
   要么升级到 eslint 9 并改写为 `eslint.config.js`（flat config）。
3. `format:check` 首次几乎一定会报一批文件——这是项目此前没有格式化工具的必然结果，
   建议执行 `npm run format` 后**单独一个提交**（"style: 统一 prettier 格式"），不要和功能改动混在一起。

## 二、Docker Compose 未做过真实构建与启动

**现状**：`docker-compose.yml`（MySQL/Redis/Agent/Java/nginx 五服务）、`docker/Dockerfile.server`、
`docker/Dockerfile.agent`、`docker/nginx.container.conf` 都已提交，并且：
- `docker compose config` 校验通过（退出码 0）；
- 用脚本把 compose 解析结果里的**每个构建上下文、Dockerfile、挂载源**逐项检查存在性 → 8/8 通过；
- Agent 与 Java 的**内部令牌由同一个 compose 变量提供**，不会出现两侧不一致导致全量 401。

未做的部分：本机只装了 Docker CLI，**Docker Desktop 引擎未启动、本地零镜像**，
启动整套需要联网拉约 2–3GB 基础镜像（mysql:8.0 / redis:7-alpine / nginx / maven / temurin / python）。

**具体怎么做**：

```bash
# 1) 启动 Docker Desktop（Windows 任务栏图标 → 等它变绿）
docker info            # 能打印 ServerVersion 才算就绪

# 2) 可选：准备好密钥，避免用默认值启动
#    在 PowerShell 里设置（或写进 .env 供 compose 读取）：
#    $env:FACTCHECK_JWT_USER_SECRET  = '<32 字节以上的随机串>'
#    $env:FACTCHECK_JWT_ADMIN_SECRET = '<32 字节以上的随机串>'
#    $env:INTERNAL_TOKEN             = '<随机串，两侧自动一致>'
#    $env:LLM_API_KEY / SEARCH_API_KEY 等按需

# 3) 构建并启动（首次需要网络，之后可离线）
cd fact-check
docker compose up -d --build

# 4) 看状态与日志
docker compose ps                 # 期望：mysql/redis 为 healthy，agent/server 为 running
docker compose logs -f server     # 期望：出现 "Started FactCheckApplication"
docker compose logs -f agent      # 期望：出现 "Uvicorn running on http://0.0.0.0:8001"

# 5) 验证入口
#    前端：http://localhost
#    接口文档：http://localhost/api/doc.html
#    Agent 健康：http://127.0.0.1:8001/health（默认只绑回环）
```

**可能的坑**：

1. **建表 SQL 只在数据卷为空时执行**（`docker-entrypoint-initdb.d` 的机制）。
   改了 `sql/` 里的建表语句后要 `docker compose down -v` 再 `up` 才会重跑（会清空数据）。
2. **端口冲突**：本机若已有 MySQL/Redis/nginx 在跑，用环境变量改映射端口：
   `$env:MYSQL_PORT=3307; $env:REDIS_PORT=6380; $env:NGINX_PORT=8081; docker compose up -d`。
3. **Agent 首次启动要下 embedding 模型**：想完全离线就把已下好的模型放进 `fact-agent/models/`，
   并在 `.env` 里设 `EMBEDDING_MODEL=/app/models/<你的模型目录名>`（compose 已把该目录挂到容器内 `/app/models`）。
4. **前端静态资源来自 `fact-check-web/dist`**：容器启动前先在宿主机 `npm run build`（本仓库已构建过一份在 `dist/`）。
5. 构建 Java 镜像时容器内会重新下载 Maven 依赖；若想完全离线，
   可在 `Dockerfile.server` 里改成直接 `COPY fact-check-server/target/*.jar`（文件里已写了两条路径说明）。

## 三、CI：GitHub Actions 已写好，但**托管在 Gitee 上不会执行**

**现状**：`.github/workflows/ci.yml` 已提交并推送成功（5 个作业：java / python / web / mini / secret-scan，
命令全部与本机验证过的一致）。**但仓库托管在 Gitee（`gitee.com/cyreneelysian/fact-check`），
Gitee 不会执行 GitHub Actions** —— 这个文件在 Gitee 上目前是"躺着不动"的。

**三种可选做法**：

**方案 A（已落地，推荐先用）：本地一键全量检查**

```powershell
cd fact-check
.\run-checks.ps1              # 跑全部 7 项：java/python/mini/web-type/web-test/compose/secret-scan
.\run-checks.ps1 -Only java,web
.\run-checks.ps1 -Online      # Maven 走在线仓库（默认 -o 离线）
```

退出码 0/1，可直接用于提交前钩子或任何 CI。**已在实机验证**：7 项全 PASS、退出码 0。

**方案 B：Gitee Go（Gitee 自带的流水线）**

Gitee 的 CI 配置放在 `.workflow/*.yml`，**语法与 GitHub Actions 不同**（trigger / pipeline / stages / step 结构），
且免费额度有限（构建时长按套餐限制）。做法：

1. 仓库页 → 「服务」→「Gitee Go」→ 开通；
2. 新建流水线，选择"自定义"，它会生成 `.workflow/<名字>.yml` 模板；
3. 把 `run-checks.ps1` 里那几条命令逐条搬进任务步骤（Gitee 的构建机是 Linux，
   把 `run-checks.ps1` 换成等价 shell 命令即可，README §9 有现成命令清单）；
4. 提交并推送，看流水线运行结果。

> 注意：Gitee Go 的 YAML schema 我无法在本机验证（没有 Gitee 构建机），因此**没有预先写一个可能跑不起来的配置文件**——
> 建议按上面的模板生成后再填命令。

**方案 C：同时镜像一份到 GitHub**

保留 `.github/workflows/ci.yml` 不动，在 GitHub 建一个镜像仓库（`git remote add github ...` + `git push github main`），
Actions 即可直接运行——该文件本来就是为 GitHub 写的，命令与本机一致。

## 四、`vite build` 的沙箱限制（已解决，附一个真实优化点）

**现状**：**已解决**。本机受限沙箱下 `vite build` 会因 esbuild 子进程管道失败（`spawn EPERM`），
且 esbuild 清理 `%TEMP%` 时被拒（`Access is denied`）。已验证可行的做法：

```powershell
# 仅在受限环境下需要：把 esbuild 的临时目录指到工作区内 + 该条命令放宽权限
$tmp = Join-Path (Get-Location) '.tmp-build'; New-Item -ItemType Directory -Force $tmp | Out-Null
$env:TEMP = $tmp; $env:TMP = $tmp
npm run build       # → ✓ built in 4.14s，dist/ 产出 35 个 assets 文件
```

**在普通机器上不需要这些**，直接 `npm run build` 即可（已验证构建成功）。
构建产物已同步到 `nginx-1.20.2/html/fact-check`（该目录未被 git 跟踪）。

**顺带发现的真实优化点**：构建警告主包过大——`index-*.js` **1,117 kB（gzip 370 kB）**，
因为 element-plus 与 vue 全被打进主包。建议在 `vite.config.ts` 加按需拆包（约 10 行，可显著改善首屏）：

```ts
build: {
  rollupOptions: {
    output: {
      manualChunks: {
        vue: ['vue', 'vue-router', 'pinia'],
        element: ['element-plus', '@element-plus/icons-vue']
      }
    }
  }
}
```

改完 `npm run build` 复查：主包应降到 300 kB 以内，element/vue 各自成为可长期缓存的独立 chunk。
