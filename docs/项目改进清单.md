## 3. 环境约束与踩坑记录（仍然有效的部分）

> 与《技术方案》《README》不重复的、值得长期留档的约束与教训。

### 3.1 `application-local.yml` 为什么不默认排除出构建产物

默认构建**会**把 `src/main/resources/application-local.yml` 复制到 `target/classes`，这是**有意的**：
IDEA 与 `mvn spring-boot:run` 运行时用的类路径就是 `target/classes`，一旦在默认构建里排除该文件，
激活 `local` profile 后 `${fact-check.datasource.*}` 会全部无法解析，启动直接失败：
`java.sql.SQLException: ${fact-check.datasource.driver-class-name}`。

构建**可分发产物**时才用 `-Pdist`（该 profile 会把 `application-local.yml` 排除在产物之外）。

> 教训：**"为了安全排除资源"必须在"本地开发也能跑"的前提下验证**，否则安全改动会变成开发阻塞。
> 这类问题应当被"启动冒烟测试"覆盖。

### 3.2 Windows venv 不可迁移

命令一律用 `python -m <模块>`（`python -m pip` / `python -m uvicorn` / `python -m app.main`）而不是
`uvicorn.exe` / `pip.exe` 这类启动器：项目文件夹一旦改名或移动，`Scripts\*.exe` 里内嵌的旧解释器绝对路径
全部失效，报 `Fatal error in launcher: Unable to create process using "...\<旧路径>\.venv\Scripts\python.exe"`。
用 `python -m` 不经过这些转发器，因此换目录后依然可用。彻底修复需删掉 `.venv` 重新创建。

### 3.3 重复启动/多次运行相关的坑

- **运行 Agent 不要加 `--workers`**：语义去重索引是进程内内存态，多 worker 会各持一份并互相覆盖。
  需要横向扩展时应改为外部向量库（Qdrant / Milvus）。
- **建表 SQL 只在数据卷为空时执行**（`docker-entrypoint-initdb.d` 的机制）：改了 `sql/` 里的建表语句后
  要 `docker compose down -v` 再 `up` 才会重跑（会清空数据）。
- **判定"服务真的起来了"的标志**：Agent 日志出现 `Uvicorn running on http://...`，
  Java 日志出现 `Started FactCheckApplication`——不要只看进程存在，否则会误报成功。

### 3.4 离线环境的依赖版本锁定（P5-74，非缺陷）

为让测试能在**离线**环境运行，`fact-check-server/pom.xml` 有三处测试范围配置：
`junit-jupiter.version=5.9.3`、显式声明 `junit-platform-launcher`、锁定 `maven-surefire-plugin=3.1.2`
（离线仓库没有 surefire 2.22.2 所需的 junit-platform provider 与 launcher 1.8.2）。
联网环境可移除这三处恢复 Boot 默认版本；保留则需保证 CI 能取到对应版本。

### 3.5 前端接口文档的两个约定（易踩）

- knife4j 只有两个**中文命名**分组，**不带 `group` 参数访问 `/api/v3/api-docs` 会 404**
  （springfox 默认找名为 `default` 的分组）。正确用法：`/api/v3/api-docs?group=用户端接口`。
- `spring.mvc.pathmatch.matching-strategy=ant_path_matcher` 与 `/api` 上下文路径是 springfox 的**必需**兼容项，
  删掉会让接口文档直接不可用（`SwaggerConfigurationTest` 已把这条锁成回归）。

### 6.6 本次修掉的一个**潜伏已久的假绿**：`$LASTEXITCODE` 与 `.Count`

`run-checks.ps1` 在 PowerShell **5.1** 下**从不因失败而返回 1**（除非"未注册的检查名"这条路径）：
`$failed = ($results | Where-Object { -not $_.Ok }).Count` —— PS 5.1 **不给管道输出的单个对象加
`.Count` 属性**（PS 7 才加），于是只有 1 项失败时 `$failed` 为 `$null`，`$null -gt 0` 为 false → `exit 0`。

同类写法还有 `$hits`（密钥扫描）与 `$unknown`（未注册检查名），均已改为 `@(...)` 包裹。
**这个 bug 暴露的契机**：新增的 `compose-env` 检查第一次产出"恰好 1 条失败"，正好命中该边界。

> 教训：PowerShell 里凡是要对管道结果取 `.Count` / 判空，一律 `@(...)` 包一层；
> 写检查脚本时更要专门构造"只有一项失败"的用例来验退出码——否则很容易做出一个"永远绿"的假防线。

| 环节 | 改动 |

### 6.8 语法预检：用编译器拦"引号没转义"，而不是用正则猜

`@DisplayName("这就是"存了但没传出去"的回归测试")` —— Java 字符串字面量里嵌**同种直引号**，
javac 报 `需要')'`；Python 同理报 `SyntaxError: unterminated string literal`。
报错位置与真正的问题（引号没转义）看起来关系不大，极难一眼定位：
本会话里 **Java 踩了三次、Python 踩了一次**。

⚠️ **我最初的方案是错的，值得留档**：想用**正则统计引号奇偶**静态拦截。三轮收窄后
在真实代码上仍有大量误报：

| 轮次 | 判据 | 真实代码误报 |
| --- | --- | --- |
| 1 | 去掉 `\"` 后引号数应为偶数 | **193 处**（`if (c == '"')` 字符字面量、Javadoc 里的中文引号） |
| 2 | `"…"…"` 且中间含 ≥2 汉字 | **88 处**（注释里的 `"安全加固"` 这类中文引号用法） |
| 3 | 再排除注释行 | **66 处**（三目 `a ? "x" : "y"`、字符串数组字面量） |
| 4 | 收窄到 `"` 紧跟中文又紧跟 `"` | **359 处**（三引号文档串） |

**结论：正则无法可靠区分"嵌套引号"与"合法多字符串"**，继续加规则只是过拟合到我自己举的例子。
而这正是 §6.6 里批评过的"永远刷屏的假防线"—— 会被无视，等于没有。

**最终方案：让编译器干这件事**（`run-checks.ps1` 第 8 项 `syntax`）：

* Java：`mvn -o -q test-compile` —— 只编译（含测试源码），**不跑测试**；
* Python：`python -m compileall -q app tests eval scripts` —— 只编译，不执行。

零误报、增量成本很小，还能顺带拦住其它语法错误。正反两向都验证过：
放入含未转义引号的探针 → FAIL（Java 报 `需要')'`、Python 报 `Error compiling`）；删除 → PASS。

> `syntax` **取代**了曾短暂存在的、基于正则的 `java-quotes`，因此项数仍是 9（不是 10）。

| `DetectRequest` | 新增可选 `category`（刻意不校验取值：分类写错、旧版 Java 不带该字段，都应退回通用提示词照常检测） |
| `detect_prompt.build_system_prompt()` | 通用提示词 + 分类专属注意事项 |

**两个设计取舍**（都写进代码注释）：

1. **不做 6 套完整 SYSTEM_PROMPT，只做"追加一段注意事项"**：整套替换意味着 6 份提示词各自
   维护一份注入防护、`<untrusted_*>` 边界与 JSON 输出契约，改一处要改六处、必然漂移，
   而漂移掉的往往正是安全约束。追加式改动影响面局限于那一段，且无对应分类时
   **行为与加固前完全一致** —— 这也让"回退"变成清空字典这一个动作。
2. **分类指导放 system message，不放 user message**：它是我们的指令、不是不可信数据；
   混进 user 消息会破坏「不可信内容一律包在 `<untrusted_*>` 标签内」的边界约定。

#### 实测结论：负向，已回退

用 `eval/category_ab.py` 做 **33 条配对对照**（同一条断言跑两次，唯一差别是 category 传不传）：

| 判据 | Baseline（不传） | Guided（传「健康」） |
| --- | --- | --- |
| 准确率 | **30/33 (90.9%)** | 29/33 (87.9%) |
| 只它命中 | — | **0 条**（一次都没救回来） |
| 只它失败 | **1 条** | — |
| 平均耗时 | 20.8s | 23.5s（**+13%**） |
| McNemar p | — | 1.0000 |

唯一差异条目 **id=39**（"血液在人体内是循环流动的"，标签 TRUE）：加指导后模型**直接拒答**
（`can_judge=false`、置信度为空），不加则正确判 TRUE —— 指导让模型变得**过度谨慎到该答的不答**。

**最值得记住的一点**：副指标**确实变好了**（推理链提到"因果 vs 相关"从 12/33 升到 20/33，
"风险等级"从 0/33 升到 5/33），**但准确率反而降了**。
这印证了报告里那句提醒 ——「模型说出了我们想让它说的话」**不等于**「判断更正确」，
它更多在复述提示词里的措辞。**副指标只能当线索，不能当证据。**

**局限**：n=33 太小，p=1.0 说明这是"**没有观察到任何好处，且观察到一处坏处**"，
而不是"统计显著的负向效果"；差异集中在 1 条上可能是运气。
但"0 条变好"不受运气影响。

**行动**：`CATEGORY_GUIDANCE` 清空；**链路完整保留**（填回文本即可重试，不必重做管线）。
`tests/test_category_prompt.py`（12 例）同时守住两件事：
① 回退状态本身（所有分类退回通用提示词、且返回的提示词不短于通用版）；
② 组装机制仍可用（临时注入指导，验证"确实会被追加、且不破坏注入防护与输出契约"）。

#### 评测脚本本身也留档（`eval/category_ab.py`）

| 项 | 设计 |
| --- | --- |
| 设计 | **配对**：同一条断言跑两次，唯一差别是 `category` 传不传 |

#### 顺手发现的独立缺陷（记为待办）：`UNVERIFIED` 被系统性判成 FALSE

3 条人工标签为 `UNVERIFIED` 的断言（"新药彻底治愈阿尔茨海默病""野生菌延寿十年"
"生吃蔬菜杀死寄生虫"），**两臂都判成 FALSE**（置信 0.80~0.97）。
而 `FALSE=19/19`、`TRUE=11/11` 全对 —— 说明模型在"非黑即白"上很强、
**在"说不清"上系统性偏错**：该转人工的判成了"假"。
这与分类提示词无关，且影响面（3/33 ≈ 9%）比分类提示词更大，值得单独修。

### 6.10 ⚠️ 事故留档：一次因缺少隔离导致的数据清空与恢复

**经过**：为验证重命名后的脚本能否按 docker 顺序执行，我**直接在真实库上 `source` 了 `01_fact_check_schema.sql`**
—— 该脚本头两行就写明"会先 DROP，请谨慎"。12 张表在 `2026-10-04 16:30:54` 被删除重建。
**根因**：验证破坏性脚本时没有做隔离（未建临时库、未先备份）。

**恢复方式**（可供以后再遇到时复用）：

1. 取证：确认 `log_bin=ON`、`binlog_format=ROW`、**`binlog_row_image=FULL`**（UPDATE 的 `### WHERE` 段带完整旧值，是恢复的关键）；
   在 binlog 里定位 DROP 的精确时间戳。
2. **隔离**：建临时库 + `mysqlbinlog --rewrite-db=源:临时库` 回放，**绝不直接在真实库上重放**。
3. 回放：从最早的可用 binlog 起、`--stop-datetime` 截止到事故前；对因早期日志过期而失败的行镜像用 `--force` 跳过并统计。
4. 校验后搬回：按依赖顺序 `REPLACE INTO` 写回，再做**逐表孤儿检查**。

**结果**：9 条检测记录（含结论/推理链/版本）、证据、账号全部找回（`admin` 的原始密码哈希也从 binlog 还原）。
**未能恢复**：`8/27–8/28` 那一段（最早的 binlog 从 `8/29 14:28` 开始，30 天保留期已清掉更早日志）——
涉及 `t_message` 早期 22 条、`t_detect_log` 早期 14 条等，业务上确认是测试数据，影响可接受。

**教训（后续必须遵守）**：凡涉及 DDL / 数据删除 / 迁移脚本的验证，先在临时库或备份上做，
并在执行前把目标库名打印出来确认；**不要相信"脚本自带的 `USE` 会保护我"**。
