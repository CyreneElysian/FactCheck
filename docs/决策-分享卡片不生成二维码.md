# 决策记录：分享卡片不生成二维码（P3-38 关闭）

> **结论：不做。** 这是**有意识的取舍**，不是"没做完"。
> 产品文档 §4.13 已按本决策同步修订，验收标准（§9 第 12 条只要求"可收藏、分享、评分"）不受影响。

## 决策理由

1. **扫码的人看到的仍是登录页**。记录详情接口 `GET /detect/record/{id}` 只允许归属者本人查看（越权保护，P0 阶段就修了）。
   二维码指向该详情页 → 别人扫出来先撞登录墙，与直接收到一条链接相比没有增量价值。
2. **小程序端已有更好的分享路径**。微信原生分享（P3-31）把卡片直接发进聊天，打开即用；
   二维码更适合线下物料（海报、展架），而本项目没有线下投放场景。
3. **成本与收益不成比例**。生成二维码需要引入编码实现（npm `qrcode`，或后端 Maven zxing），
   属于"为低价值功能增加一个依赖与维护面"。当前分享卡片改为打印**记录链接**，功能上可替代。

## 当前实现（已完成）

Web 端 `HistoryDetailView.drawShareCard` 用原生 canvas 生成分享卡片：消息摘要（最多 5 行）+ 结论 +
**记录链接**（`${origin}/history/{id}`）+ 平台标识，可下载为 PNG。小程序端为微信原生分享（含朋友圈）。

## 如果将来要补做（线下投放等场景）

不引入前端依赖、且**可自动化验证**的做法是后端出图（编码后立刻解码断言内容一致）：

1. `fact-check/pom.xml` 的 `dependencyManagement` 加 `com.google.zxing:core` 与 `javase`（3.5.3）；
2. 新增 `QrCodeUtil.png(text, size)`：`QRCodeWriter().encode(...)` + `MatrixToImageWriter.writeToStream(...)`；
3. `CommonController` 加 `GET /common/qrcode?text=...`（`produces = IMAGE_PNG_VALUE`，入参长度校验 300），
   并把 `/common/**` 纳入用户端 JWT 拦截器路径（**当前 `/common/upload` 也未鉴权，属于待修的越权面**）；
4. 前端在分享卡片里 `new Image()` 加载该接口并把图画进 canvas；
5. 测试：编码 → `MultiFormatReader` 解码 → 断言文本一致。

> 为什么当时没有手写一个二维码编码器：QR 涉及 Reed-Solomon 纠错、掩码选择、格式/版本信息，
> 错一位的结果是"看着像二维码但扫不出来"；而本机既无参考实现可逐位比对、也无解码器可反向验证
> （npm registry 不可达、缓存 `ENOTCACHED`；离线 Maven 仓库无 zxing；venv 无二维码库）。
> 写一个无法验证的实现会把问题伪装成已完成，因此当时选择了明确记录方案而不是硬做。
