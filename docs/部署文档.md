## 1. 部署前必读

### 1.1 架构与端口

```
浏览器 ──► Nginx :80 ──┬── /            → 前端 SPA 静态资源（fact-check-web/dist）
                        └── /api/        → Java 后端 :8080（context-path=/api）
                                              ├── MySQL :3306   （关系数据，12 张表）
                                              ├── Redis :6379   （热度榜 ZSET / 限流 / 查看去重）
                                              └── Python Agent :8001（语义去重 + 检索 + LLM，仅内网调用）
微信小程序 ─────────────────────────────────────► 同一个 /api
```

**关键约定（踩过的坑，务必遵守）**

| 约定 | 原因 |
| --- | --- |
| Nginx 里**不要**单独配 `location /admin/` 或 `/user/` | 它们的优先级高于 `location /`，会截获 SPA 路由 → 刷新页面 404 |
| `/api/` 反代必须传 `X-Real-IP` 与 `X-Forwarded-For` | 后端按这两个头取真实 IP 做限流，缺了会把所有请求算成同一个 IP（限流误伤） |
| Python Agent 默认只监听 `127.0.0.1:8001` | 它只该被同机 Java 调用；暴露到 `0.0.0.0` 会让"内部接口"变成"局域网可访问" |
| 容器里**只激活 `dev` profile**，不要带 `local` | `application-local.yml` 里写死 `localhost`/`root`，容器内会把服务名覆盖成 `localhost` → 连不上库（详见 §3.2） |

### 1.2 环境要求

| 依赖 | 版本 | 说明 |
| --- | --- | --- |
| JDK | **11+** | 项目按 Java 11 编译（`maven.compiler` 11） |
| Maven | 3.8+ | 离线环境需预热本地仓库（见 §4.5） |
| Node.js | 18+ | 生产构建用；`npm run test:offline` 需 **≥22.6** |
| MySQL | **8.0** | DDL 用了 `utf8mb4_unicode_ci` 与 `CHECK` 之外的 8.0 特性 |
| Redis | 5+（推荐 7） | 用到 ZSET、Lua `EVAL`、`SET NX EX` |
| Python | **3.10** | Agent 与演示数据脚本；虚拟环境不可跨机拷贝（见 §7.3） |
| Nginx | 1.20.2（仓库自带）或任意 1.20+ | 仓库里 `nginx-1.20.2/` 只保留了 `conf/` 与占位页面 |
| Docker（可选） | 20.10+ / Compose v2 | 容器化路线，见 §3 |

### 1.3 初始化口令（⚠️ 部署后必须立刻改）

| 账号 | 口令 | 角色 | 来源 |
| --- | --- | --- | --- |
| `admin` | `123456` | 管理员 | `sql/02_fact_check_init.sql` |
| `demo_user` / `demo_admin` | `123456` | 普通 / 管理 | `fact-check/scripts/generate_test_data.py` |

**全部为弱口令。** 项目现已强制密码强度（注册 / 改密 / 管理员建号：8–64 位且含字母+数字、
不在弱口令黑名单、不等于用户名），但**登录不校验强度** —— 因此库里已有的这些弱口令仍能登录，
必须**手工改掉**（改密时会被强制变强）。这样设计是为了避免"一次安全加固把现有账号锁在门外"。

## 2. 部署路线选择

| 路线 | 适合 | 优点 | 代价 |
| --- | --- | --- | --- |
| **A. 容器化（Compose）** | 新机器、快速起全套、要可重复 | 一条命令起 5 个服务；MySQL 首次启动自动建库建表 | 首次构建需联网（基础镜像 + Maven/pip 依赖 + embedding 模型）；镜像较大 |
| **B. 裸机（手工）** | 已有 MySQL/Redis、要调参、要离线 | 无 Docker 依赖；可完全离线 | 需自己装齐 5 套环境；顺序与端口要自己保证 |

两条路线**共用同一份 `sql/`、同一份 `application-dev.yml`**，因此配置变量的含义一致，只是注入方式不同。

## 3. 路线 A：容器化部署（Compose）

### 3.1 前置

- Docker Engine 正在运行（Windows 用 Docker Desktop；**需启用 Linux 容器**）
- 首次构建可访问外网

验证引擎可用：

```bash
docker info --format '{{.ServerVersion}}'     # 有版本号输出即正常
docker compose version                         # 必须能打印版本，见 §3.1.1
docker compose config --quiet && echo "compose 语法 OK"
```

### 3.1.1 ⚠️ 前置排障：`docker compose` 报 `unknown shorthand flag: 'd'`

症状：

```
$ docker compose up -d --build
unknown shorthand flag: 'd' in -d
Usage:  docker [OPTIONS] COMMAND [ARG...]
```

**这不是 compose 文件的问题，而是 `docker` CLI 根本没识别出 `compose` 子命令** ——
它把 `-d` 当成了 `docker` 自己的参数。原因：Compose 是 Docker CLI 的**插件**，`docker` 只在固定目录里找它，
而 Docker Desktop 自带的插件放在 `resources\cli-plugins\`，该目录**不在**默认搜索路径里
（`~/.docker/config.json` 里也没有 `cliPluginsExtraDirs`），于是插件发现失败。

**判断方法**：

```bash
docker compose version          # unknown command: docker compose → 确认是这个问题
docker-compose --version        # 若这条能打印版本，说明二进制存在、只是没被识别为插件
ls ~/.docker/cli-plugins        # 空目录 = 根因
```

**修法 A（最省事，零配置）：直接用独立二进制**

```bash
docker-compose up -d --build
# 下文所有 `docker compose xxx` 都可等价替换为 `docker-compose xxx`（命令与参数完全一致）
# 本机实测：resources\bin\docker-compose.exe 为 v5.4.0，功能完整
```

**修法 B（推荐，恢复 `docker compose` 子命令）：用 `cliPluginsExtraDirs` 告知 CLI**

```powershell
# Windows PowerShell —— 在 ~/.docker/config.json 里加一个键，指向 Docker Desktop 的插件目录
$cfg = "$env:USERPROFILE\.docker\config.json"
$obj = Get-Content $cfg -Raw | ConvertFrom-Json
$dir = "$env:LOCALAPPDATA\Programs\DockerDesktop\resources\cli-plugins"
$dirs = @($obj.cliPluginsExtraDirs) + $dir | Where-Object { $_ } | Select-Object -Unique
$obj | Add-Member -NotePropertyName cliPluginsExtraDirs -NotePropertyValue $dirs -Force
[System.IO.File]::WriteAllText($cfg, ($obj | ConvertTo-Json -Depth 10), (New-Object System.Text.UTF8Encoding($false)))
docker compose version          # 立即生效，无需重启 Docker Desktop
```

> **`config.json` 会被 CLI 立即重新读取，不用重启 Docker Desktop**（改 `daemon.json` 才需要重启）。

**❌ 不要用"复制插件到 `~/.docker/cli-plugins`"这个网上常见的办法**

本机实测：复制过去后 `docker compose` 确实能用，但**重启 Docker Desktop 后该文件被清掉了**，
又变回 `unknown command`。那个目录由 Docker Desktop 自己管理，手工放进去的东西不持久。
（相关目录里 Docker Desktop 自带 15 个插件：`docker-buildx` / `docker-compose` / `docker-scout` …，
用修法 B 一次性全部生效。）

### 3.1.2 建议：先分三步验证，再一次性起全套

`up -d --build` 一条命令同时做四件事（拉镜像、装 Maven 依赖、装 pip 依赖、起 5 个服务），
失败时很难定位在哪一层。建议按下面顺序推进：

```bash
# 第 1 步：只起不构建的三个服务（几十秒）——验证镜像能拉、SQL 初始化顺序、前端静态托管
docker compose up -d mysql redis nginx
docker compose ps                                    # mysql/redis 应为 healthy
docker compose exec mysql mysql -u root -p"$MYSQL_ROOT_PASSWORD" \
  -e "select username, role from fact_check.t_user"  # 应看到 admin/1（证明 01→02 顺序正确）
curl -s -o /dev/null -w '%{http_code}\n' http://localhost/    # 200

# 第 2 步：构建 Agent（最慢，要装 pip 依赖；模型走只读挂载不用下载）
docker compose up -d --build agent
docker compose logs agent | tail -20                 # 看启动自检三字段

# 第 3 步：构建后端
docker compose up -d --build server
docker compose logs -f server                        # 等 Started FactCheckApplication
```

分步走的好处：每步只引入一个新变量，出问题能直接锁定到"镜像拉取 / SQL 顺序 / pip 依赖 / Maven 依赖 / 应用配置"中的哪一层。

### 3.1.3 ⚠️ 拉镜像失败：`unexpected media type text/html`

症状（三个基础镜像全部 `Interrupted`）：

```
failed to unpack image on snapshotter overlayfs:
unexpected media type text/html for sha256:c0fc0af8...: not found
```

**怎么读这个报错**：Docker 期望拿到镜像层（二进制 tar.gz，`application/vnd.oci.image.layer...`），
实际拿到的是 `text/html` —— 说明**中间某处返回了一个 HTML 页面**（失效镜像源的错误页 / 网络拦截页）。
所以这**不是 compose 或 Docker 的问题，是拉取链路的问题**。

#### 最常见的原因：`registry-mirrors` 里堆了一大串**失效**的源

很多"一键配置脚本"会往 `daemon.json` 塞十几二十条公共镜像源。Docker 会**按顺序逐个尝试**，
撞上失效源就会超时或拿到 HTML 错误页。**本机实测**：原列表有 **21 条**，其中只有 1 条可用
（还混着一个占位符 `https://your_preferred_mirror`）—— 这不是"没配镜像源"，而是"配了一堆坏的"。

**第一步：把列表打印出来看**

```bash
docker info --format '{{.RegistryConfig.Mirrors}}'
```

**第二步：逐个探测，只留实测能通的**

```powershell
foreach ($m in 'https://docker.1panel.live','https://docker.m.daocloud.io','https://hub.rat.dev',
               'https://docker.xuanyuan.me','https://dockerpull.org','https://mirror.ccs.tencentyun.com') {
  try { $c=(Invoke-WebRequest "$m/v2/" -Method Head -TimeoutSec 6 -UseBasicParsing).StatusCode; "$m -> $c ✓" }
  catch { "$m -> 不通" }
}
```

判定标准：**`200` 或 `401` 都算可用**（`/v2/` 本来就需要认证，`401` 是正常的"服务器活着"的响应）；
超时或连接失败就是不可用。本机实测 `https://docker.1panel.live` 返回 **200**。

**第三步：写 `daemon.json`（只留测通的那几条）**

文件位置：`%USERPROFILE%\.docker\daemon.json`

```json
{
  "builder": { "gc": { "defaultKeepStorage": "20GB", "enabled": true } },
  "experimental": false,
  "features": { "buildkit": true },
  "registry-mirrors": ["https://docker.1panel.live"]
}
```

> ⚠️ **这个文件里可能已有别的设置，务必"读-改-写"，不要整文件覆盖**（本机就因为这个丢过
> `builder.gc` / `experimental` / `features` 三项）。先备份：`copy daemon.json daemon.json.bak`。

**第四步：重启 Docker Desktop，然后验证**

```bash
# 托盘图标 → Quit Docker Desktop → 重新启动 → 等图标变绿
docker info --format '{{.RegistryConfig.Mirrors}}'    # 应只显示你配置的那几条
docker pull redis:7-alpine                            # 先拉一个小镜像试水，成功再 up
```

#### 其它原因与对策

| 现象 | 原因 | 对策 |
| --- | --- | --- |
| 所有镜像源都不通，但能上普通网站 | 网络对 registry 域名做了拦截 | 用代理：在 `daemon.json` 里加 `"proxies": {"http-proxy": "http://127.0.0.1:<端口>", "https-proxy": "...", "no-proxy": "localhost,127.0.0.1"}`，或走 Docker Desktop → Settings → Resources → Proxies 图形界面 |
| 公司内网、完全无外网 | 没有出网通道 | 用公司内网 registry；或在他处 `docker save` 成 tar 再 `docker load` |
| 只有某个镜像失败 | 该仓库在镜像源上不存在 | 显式带源前缀拉取：`docker pull docker.1panel.live/library/redis:7-alpine` |

### 3.2 必读：`docker-compose.yml` 里三个**必须知道**的点

**① 后端的环境变量名与 `application-dev.yml` 的占位符一一对应**

`application.yml` 的 JDBC URL 是**拼装**出来的：

```yaml
url: jdbc:mysql://${fact-check.datasource.host}:${fact-check.datasource.port}/${fact-check.datasource.database}?...
```

所以**不能**用 `FACTCHECK_DATASOURCE_URL` 之类的变量整体覆盖（那变量代码里不存在），必须用
`FACTCHECK_DB_HOST` / `FACTCHECK_DB_PORT` / `FACTCHECK_DB_NAME` / `FACTCHECK_DB_USERNAME` / `FACTCHECK_DB_PASSWORD`。

> 这三处历史上写错过，症状是后端报 `Communications link failure`（一直在连 `localhost:3306`）。现已修正。

**② 容器里必须只激活 `dev`：`FACTCHECK_PROFILE: dev`**

`application.yml` 的默认值是 `${FACTCHECK_PROFILE:dev,local}`。本机跑时 `local` 用
`application-local.yml` 覆盖 `dev`（方便），但那个文件里写死了 `host: localhost` / `username: root` /
`password: "1234"`。`application-local.yml` **默认会被打进 jar**（打包脚本只在 `-Pdist` 时排除它），
因此容器里若沿用默认的 `dev,local`，上面那批环境变量会被 `local` 全部覆盖 → 连不上 `mysql` 服务。
`docker-compose.yml` 已显式设 `FACTCHECK_PROFILE: dev`，**不要删这一行**。

**③ `sql/` 目录按文件名字典序执行，且不递归子目录**

MySQL 官方 entrypoint 会按文件名顺序 `source` `/docker-entrypoint-initdb.d/*.sql`。因此：

- `01_fact_check_schema.sql`（建库建表）必须排在 `02_fact_check_init.sql`（初始管理员）**之前**——前缀是必需的；
- `sql/migrations/` 在子目录里，**不会**被自动执行（这是刻意的：迁移只针对已存在的库，新库由 schema 脚本直接建成最新结构）。

### 3.3 起服务

```bash
# 1) 前端先在本机构建（compose 只挂载 dist 目录，不在容器里构建前端）
cd fact-check-web
npm install
npm run build                     # 产物：fact-check-web/dist

# 2) 回项目根，准备密钥（强烈建议：不要用默认值）
cd ..
cp fact-agent/.env.example fact-agent/.env
#    编辑 fact-agent/.env：填 LLM_API_KEY、SEARCH_TOOL/SEARCH_API_KEY，并把 INTERNAL_TOKEN 换成随机值

export INTERNAL_TOKEN=$(openssl rand -hex 32)      # 与 fact-agent/.env 里保持一致
export FACTCHECK_JWT_USER_SECRET=$(openssl rand -hex 32)
export FACTCHECK_JWT_ADMIN_SECRET=$(openssl rand -hex 32)
export MYSQL_ROOT_PASSWORD=<强口令>
export MYSQL_PASSWORD=<强口令>

# 3) 构建并启动
docker compose up -d --build
docker compose ps                 # 五个服务应逐渐变为 healthy / running
```

### 3.4 变量清单（Compose）

| Compose 变量 | 默认值 | 作用 |
| --- | --- | --- |
| `MYSQL_ROOT_PASSWORD` | `factcheck_root` | MySQL root 口令 |
| `MYSQL_USER` / `MYSQL_PASSWORD` | `factcheck` / `factcheck_pass` | 应用连接用的账号（**不要用 root 跑应用**） |
| `MYSQL_PORT` / `REDIS_PORT` / `SERVER_PORT` / `NGINX_PORT` | 3306 / 6379 / 8080 / 80 | 宿主机映射端口 |
| `AGENT_BIND` / `AGENT_PORT` | `127.0.0.1` / 8001 | Agent 默认只绑回环，需要本机调试才开放 |
| `INTERNAL_TOKEN` | `dev-internal-token-change-me` | **Java ↔ Agent 的内部令牌，两侧由同一个变量注入**，不一致会全量 401 |
| `FACTCHECK_JWT_USER_SECRET` / `FACTCHECK_JWT_ADMIN_SECRET` | 空 | 用户端 / 管理端 JWT 密钥（空则用 `application.yml` 里的开发默认值，**生产必须注入**） |
| `FACTCHECK_OSS_ACCESS_KEY_ID` / `_SECRET` | 空 | 图片上传（留空则上传接口不可用，其余功能正常） |
| `FACTCHECK_WECHAT_APP_ID` / `_SECRET` | 空 | 小程序登录（留空则小程序登录不可用） |

### 3.5 健康检查与验收

Compose 已为每个服务配了 healthcheck，可直接用它做验收：

```bash

curl -s -o /dev/null -w '%{http_code}\n' http://localhost/api/doc.html     # 200
```

### 3.6 常用运维

```bash
docker compose logs -f server           # 后端日志（找 Started FactCheckApplication）
docker compose logs -f agent            # Agent 日志（启动自检会打印 search_offline / llm_configured / internal_auth）
docker compose restart server           # 只重启后端
docker compose down                     # 停止（保留数据卷）
docker compose down -v                  # ⚠️ 连数据卷一起删：MySQL/Redis/Agent 数据全丢
docker compose up -d --build server     # 改了 Java 代码后重建单个服务
```

⚠️ **`down -v` 会删掉 `mysql-data` 卷**。要重来一遍初始化（让 `sql/` 重新执行）才需要它。

### 3.7 一键脚本 `start-docker.ps1`（推荐，尤其网络受限环境）

```powershell
.\start-docker.ps1 check      # 只做环境自检，不做任何变更
.\start-docker.ps1            # 生成密钥 → 构建镜像（缺时才建）→ 起容器 → 健康检查 → 冒烟验收
.\start-docker.ps1 down       # 停止容器（保留数据卷）
.\start-docker.ps1 down -PurgeData   # 停止并删数据卷（会二次确认）
```

**参数**：

| 参数 | 作用 |
| --- | --- |
| `-NewSecrets` | 强制重新生成 JWT 密钥（默认复用当前会话里的） |
| `-Recreate` | `up` 时先删容器再重建 —— **换了密钥后必须用它**，否则新密钥不会注入 |
| `-TimeoutSeconds` | 健康检查等待上限，默认 180 |
| `-PurgeData` | 仅对 `down` 有效，连数据卷一起删 |

**脚本自动处理的四件事**（都是实际踩过的坑）：

| 自动行为 | 解决的坑 |
| --- | --- |
| 生成/复用两个 JWT 密钥（64 字符十六进制） | 不设密钥 → 登录返回"未知错误"（§11.6）。密钥**只在内存里**，不落盘 |
| 80 被占用时自动改用 8081 | 零信任/VPN 客户端占 80（§11.2） |
| 检测"运行中容器里的密钥"与当前 shell 是否一致 | 换了密钥但没重建容器 → token 莫名失效（提示用 `up -Recreate`） |
| 没有 `fact-check-server` 镜像时用离线 Dockerfile 构建 | 容器内 Maven 下载不稳（§11.4） |

> 脚本内部有两个 PowerShell 细节值得注意（都踩过）：`$ErrorActionPreference='Stop'` 会让 docker 写到
> **stderr** 的正常错误直接终止脚本；`$LASTEXITCODE` 一接管道就会被重置为 -1。
> 因此所有外部命令都走统一的 `Invoke-Native` 封装。

## 4. 路线 B：裸机部署

### 4.1 顺序总览

```
① MySQL 建库建表 + 初始管理员  →  ② Redis  →  ③ Python Agent  →  ④ Java 后端  →  ⑤ 前端构建  →  ⑥ Nginx
```

Agent 与 Java 谁先起都行，但**Java 的健康检查依赖 MySQL/Redis**（连不上会启动失败），所以要先把外部依赖起好。

### 4.2 ① 初始化数据库

#### 4.6.1 ⚠️ Windows：`remove ...\Temp\esbuild-<hash>: Access is denied`

完整报错形态（注意 **模块转换其实已经成功**）：

```
✓ 1733 modules transformed.
x Build failed in 4.78s
error during build:
[vite:esbuild-transpile] remove C:\Users\<你>\AppData\Local\Temp\esbuild-<hash>: Access is denied.
```

**这是环境问题，不是代码或配置问题**：esbuild 转换完模块后要删掉自己的临时文件，删不掉。
常见原因：

1. **安全软件 / 零信任客户端**（如深信服 aTrust）在文件句柄尚未释放时扫描并锁住它；
2. **OneDrive 等同步盘**正在同步 `%TEMP%` 下的文件；
3. `%TEMP%` 目录 ACL 被收紧。

**本仓库已内置规避，且已实测通过**：`npm run build` 指向 `scripts/build.mjs`，它在启动 vite
**之前**把 `TMP` / `TEMP` / `TMPDIR` 指向项目内的 `fact-check-web/.tmp/`（已 gitignore）。
安全软件通常不会盯着项目目录，因此即通过。

```powershell
# 想确认包装脚本把临时目录指到了哪，可干跑：
node scripts/build.mjs --print
# [build] TMP/TEMP : <项目>\fact-check-web\.tmp
# [build] command  : npx.cmd vite build
```

> **为什么不用 `.npmrc` 的 `tmp=...`**：**npm 不支持这个配置项**（会打印
> `Unknown project config "tmp"`），设了也不生效。esbuild 读的是进程环境变量，
> 必须在 spawn vite 之前改好——这正是 `scripts/build.mjs` 存在的原因。
> `.npmrc` 里只保留 `cache=.npm-cache`（这个是有效配置）。
>
> **包装脚本自身的两个坑**（都已在注释里留档）：
> `spawn('npx.cmd', args, { shell: true })` 会触发 Node 18+ 的 **DEP0190** 告警；
> 去掉 `shell` 又会在 Windows 上 **EINVAL**（Node 不能直接 spawn `.cmd`）。
> 最终写法是把可执行文件与参数**拼成一条命令字符串**配 `shell: true`、不传 args 数组。

**如果仍然失败**，按顺序试：

```powershell
# 1) 换一个不受监控的临时目录（例如用户目录下自建）
$env:TEMP = "$env:USERPROFILE\build-tmp"; $env:TMP = $env:TEMP
New-Item -ItemType Directory -Force $env:TEMP | Out-Null
npm run build

# 2) 把项目移出 OneDrive / 同步盘目录

# 3) 临时暂停安全软件的文件监控（仅构建期间），或把项目目录加入白名单
```

> 顺带说明：直接在 shell 里跑 `node scripts/xxx.mjs` **不会**读到 `.npmrc`，
> 也就不经过这层包装。那种情况请先手动设好 `$env:TEMP`。

#### 4.6.2 拆包效果（实测）

`vite.config.ts` 已加 `manualChunks`，把两个"体积大但很少变"的依赖拆成独立 chunk。
本机实测（2026-10-04）：

| chunk | 体积 | gzip |
| --- | --- | --- |
| `element-*.js` | 938.9 kB | 301.8 kB |
| `vue-*.js` | 110.9 kB | 43.3 kB |
| **`index-*.js`（业务主包）** | **67.2 kB** | **26.2 kB** |
| `index-*.css` | 362.1 kB | 48.4 kB |

**意义**：拆包**不减小总体积**（element-plus 该多大还是多大），但它把"缓存失效的范围"
从 1093 kB 缩到 67 kB —— 业务代码改一行，用户只需重下 67 kB，vue/element 直接命中浏览器缓存。

> 注意首屏仍会加载 element chunk（`index.html` 直接引用了它，因为布局与登录页就要用 element-plus）。
> 要真正减小首屏，需要按需引入（`unplugin-vue-components`）——那是另一件事，不要在拆包任务里混做。

可用校验（都应通过）：

```bash
npm run type-check       # vue-tsc，含模板类型检查
npm run lint             # eslint
npm run format:check     # prettier
npm run test:run         # vitest（沙箱/CI 受限时用 npm run test:offline）
```

### 4.9 两个易踩的环境细节

**① Windows 下 Python 虚拟环境不可迁移 —— 命令一律用 `python -m`**

用 `python -m pip` / `python -m uvicorn` / `python -m app.main`，
**不要**用 `pip.exe` / `uvicorn.exe` 这类启动器：项目文件夹一旦改名或移动，
`Scripts\*.exe` 里内嵌的旧解释器绝对路径全部失效，会报

```
Fatal error in launcher: Unable to create process using "...\<旧路径>\.venv\Scripts\python.exe"
```

`python -m` 不经过这些转发器，换目录后依然可用。彻底修复需删掉 `.venv` 重新创建。

**② knife4j 接口文档必须带 `group` 参数**

只有两个**中文命名**的分组，**不带 `group` 访问 `/api/v3/api-docs` 会 404**
（springfox 默认找名为 `default` 的分组）。正确用法：

```
/api/v3/api-docs?group=用户端接口
```

另外 `spring.mvc.pathmatch.matching-strategy=ant_path_matcher` 与 `/api` 上下文路径
是 springfox 的**必需**兼容项，删掉会让接口文档直接不可用
（`SwaggerConfigurationTest` 已把这条锁成回归）。

## 7. 故障排查（按症状）

### 7.0 `docker compose` 报 `unknown shorthand flag: 'd'`

`compose` 子命令没被识别（不是 compose 文件的问题）。完整说明与两种修法见 **§3.1.1**；
最快是改用独立二进制 `docker-compose up -d --build`。

### 7.1 后端启动失败：`Communications link failure`

按顺序查：

1. `FACTCHECK_DB_HOST` 是否为 `mysql`（容器）或实际主机名（裸机）——**不能是 `localhost`（容器内即自己）**；
2. 是否误激活了 `local` profile（见 §3.2 ②）：日志里搜 `The following profiles are active`；
3. MySQL 容器是否 healthy：`docker compose ps`；
4. 账号权限：应用**不应**用 root；确认 `MYSQL_USER` 对 `fact_check` 库有权限。

### 7.2 后端 401 全量失败（Agent 调用）

Java ↔ Agent 的 `INTERNAL_TOKEN` 不一致。两侧都检查：

```bash
docker compose exec server env | grep INTERNAL
docker compose exec agent  env | grep INTERNAL_TOKEN
```

裸机则是 `fact-agent/.env` 的 `INTERNAL_TOKEN` 与 `FACTCHECK_AGENT_INTERNAL_TOKEN` 要对齐。
**留空 = fail-closed，内部接口一律 401**（这是有意的设计）。

### 7.3 Agent 起不来

| 症状 | 原因 | 处理 |
| --- | --- | --- |
| `No module named app` | 用了 `.venv\Scripts\uvicorn.exe` 直调 | 改用 `python -m app.main` |
| 首次启动卡在下载模型 | 需要联网拉 `BAAI/bge-small-zh-v1.5` | 预先把模型放到 `fact-agent/models/` 并改 `EMBEDDING_MODEL` |
| `model load failed` | 离线且模型缺失 | 同上报；此时**去重会退化为不可用**，检测主流程仍可跑 |
| venv 从别的机器拷过来 | venv 里写死了绝对路径，**不可迁移** | 在目标机重建 venv |

### 7.4 前端刷新 404

nginx 里多配了 `location /admin/` 或 `/user/`，截获了 SPA 路由。删掉它们，只保留
`location /` 的 `try_files $uri $uri/ /index.html`。

### 7.5 限流把正常用户拦了

后端按 `X-Real-IP` / `X-Forwarded-For` 取真实 IP。若 nginx 没传这两个头，所有请求算同一个 IP
→ 触发 `login-per-ip`（默认 20 次/10 分钟）。补上 proxy_set_header 即可。
临时放宽用环境变量：`FACTCHECK_RATE_LIMIT_LOGIN_PER_IP`、`FACTCHECK_RATE_LIMIT_LOGIN_PER_USERNAME`。

### 7.6 `docker compose up` 时 MySQL 容器反复重启

多半是 `sql/` 里某个脚本报错（entrypoint 是 `set -e`，报错即退出）。看日志：

```bash
docker compose logs mysql | tail -50
```

常见原因是文件名字典序不对（`init` 排在 `schema` 前面），见 §3.2 ③。

### 7.7 改了代码但容器里没生效

Compose 用的是**构建产物**。Java 改动需 `docker compose up -d --build server`；
前端改动需在宿主机重新 `npm run build`（容器只挂载 `dist`，不会替你构建）。

### 7.8 登录返回「未知错误」（密码明明是对的）

**先查一个反直觉的点**：`t_user.last_login_time` 是否被更新了？

```powershell
docker compose exec mysql mysql -u root -pfactcheck_root \
  -e "select username, last_login_time from fact_check.t_user"
```

**若 `last_login_time` 是刚才的时间** → 密码校验、写库都已成功，异常出在**签发 token**：
**JWT 密钥被注入成了空字符串**。完整因果链与两处修复见 **§11.6**。

快速自检：

```powershell
docker compose exec server env | Select-String 'JWT'
# 密钥为空 → 就是这个问题
```

### 7.9 零信任 / VPN 客户端导致 localhost 异常、80 端口被占

症状：`curl http://localhost/` 返回的不是你的项目（例如 `307 → /apps`）、
`wsl --status` 报 `E_ACCESSDENIED`、Docker Hub 连不上。见 **§11.2**。

### 7.10 容器内 Maven 构建卡住或报传输截断

```
Premature end of Content-Length delimited message body
```

见 **§11.4**：根因通常是 surefire 版本未全局固定 + 网络不稳定；
用 `fact-check/Dockerfile.server.local` 走"只拷 jar"的离线路线可完全绕开。

### 7.11 改了 `sql/` 里的建表语句，重启后没生效

**建表脚本只在数据卷为空时执行一次**（`docker-entrypoint-initdb.d` 的机制）。
改了 `sql/` 后必须**连数据卷一起删**才会重跑：

```bash
docker compose down -v      # ⚠️ -v 会删掉 mysql-data / agent-data / redis-data 卷，数据全丢
docker compose up -d --build
```

只想改结构又不想丢数据时，走 §5 的迁移流程（`sql/migrations/`），不要 `down -v`。

### 7.12 宿主机上已有 MySQL / Redis / nginx，端口冲突

本机若已跑着这些服务，用环境变量改映射端口再启动：

```powershell
$env:MYSQL_PORT = 3307; $env:REDIS_PORT = 6380; $env:NGINX_PORT = 8081
docker compose up -d
```

### 7.13 前端打开是旧的 / 是默认页

compose **只挂载 `fact-check-web/dist`，不在容器里构建前端**。改完前端必须先在宿主机构建：

```bash
cd fact-check-web && npm run build
```

再 `docker compose restart nginx`（或 `up -d`）。另外 `fact-check-web/dist` 与
`nginx-1.20.2/html/fact-check` **都未被 git 跟踪** —— 新克隆的仓库里没有它们，必须先构建。

### 7.14 Agent 首次启动卡在下载 embedding 模型

想完全离线就把已下好的模型放进 `fact-agent/models/`，
并在 `fact-agent/.env` 里设 `EMBEDDING_MODEL=/app/models/<模型目录名>`
（compose 已把该目录挂到容器内 `/app/models`，只读）。

## 11. 网络受限环境部署实录（2026-10-04，真实踩坑）

> 本节记录一次**从零到跑通**的完整过程。环境特点：校园网 + **深信服 aTrust 零信任客户端** +
> Docker Desktop（Windows/WSL2）。这些坑在公司内网、校园网很常见，且**每条报错都极具误导性**。
> 按遇到顺序排列。

### 11.1 `docker compose` 报 `unknown shorthand flag: 'd'`

见 §3.1.1。**根因**：Compose 插件不在 CLI 搜索路径（`~/.docker/cli-plugins` 为空、
`config.json` 无 `cliPluginsExtraDirs`）。
**注意**：网上常见的"把 `docker-compose.exe` 复制到 `~/.docker/cli-plugins`"**不持久** ——
本机实测复制后能用，但**重启 Docker Desktop 后该文件被清掉**。正确做法是 `cliPluginsExtraDirs`。

### 11.2 ⚠️ 深信服 aTrust 劫持 `localhost` 并占用 80 端口

**症状**：`curl http://localhost/` 返回 `307` 且 `Server: nginx/1.31.4`、`location: /apps` ——
但 `docker compose ps` 显示**没有任何容器**。

**排查**：

```powershell
# hosts 被写入了一行
Select-String 'localhost' C:\Windows\System32\drivers\etc\hosts
#   127.0.0.1    localhost.sangfor.com.cn
curl.exe -s -i --noproxy '*' http://127.0.0.1/     # 连 127.0.0.1 也被接管 → 307 → /apps
Get-NetTCPConnection -LocalPort 80 -State Listen    # 0.0.0.0:80 被占（进程名不可见）
Get-Process | Where-Object { $_.ProcessName -match 'sangfor|aTrust' }
Get-ChildItem 'C:\Program Files (x86)\Sangfor'      # → aTrust
```

**结论**：零信任客户端把**本机 80 端口的 HTTP 流量全部接管**到自己门户，并写入 hosts。
这同时解释了三个看似无关的现象：

| 现象 | 真实原因 |
| --- | --- |
| `wsl --status` 报 `Wsl/E_ACCESSDENIED` | aTrust 拦截虚拟化调用，而 Docker Desktop 的 Linux 容器正依赖 WSL2 |
| Docker Hub 直连超时、部分技术站点不通 | 流量被它的策略接管 |
| 容器 nginx 无法绑定 80 | 80 已被它占用 |

**处置**：

```powershell
$env:NGINX_PORT = '8081'      # 换端口即可，不必动 aTrust
docker compose up -d
# 之后一律用 127.0.0.1 访问，不要用 localhost
```

**更彻底的方案**（可选，需你评估）：在 aTrust 里把 `*.docker.io`、`registry-1.docker.io`、
`repo.maven.apache.org` 等加入**直连/排除**列表；或在构建镜像时临时退出该客户端。

### 11.3 拉镜像报 `unexpected media type text/html`

见 §3.1.3。**根因**：`daemon.json` 的 `registry-mirrors` 里堆了 **21 条**公共镜像源（含占位符
`https://your_preferred_mirror`），其中只有 1 条可用。Docker 按序重试，撞上失效源就拿到 HTML 错误页。
**处置**：逐个 `HEAD /v2/` 探测（`200`/`401` 都算可用），只留测通的那条（本机为
`https://docker.1panel.live`）。

> ⚠️ **写 `daemon.json` 务必"读-改-写"**。本机第一次直接整文件覆盖，把原有的
> `builder.gc` / `experimental` / `features` 三项写掉了（已还原）。先备份再改。

### 11.4 容器内构建报 `Premature end of Content-Length delimited message body`

**症状**：`RUN mvn -B -q clean package -DskipTests` 跑了 30 分钟后失败：

```
Could not transfer org.apache.maven.surefire:surefire-logger-api:jar:2.22.2 from/to central:
Premature end of Content-Length delimited message body (expected: 13,346; received: 10,024)
```

**两个叠加的原因**：

1. **网络对 Central 是"通但不稳"**（能下、会截断）—— 不是彻底不通；
2. **`maven-surefire-plugin` 版本只在 `fact-check-server` 里覆盖成 3.1.2，父 pom 没有全局指定**，
   于是 `fact-check-common` / `pojo` 仍用 Spring Boot 2.7.3 默认的 **2.22.2**，而该构件必须联网现下。
   （项目注释里早已记录"离线仓库没有 2.22.2"这个坑，只是没推广到父 pom —— 属项目级缺陷。）

**已修**：父 pom 加 `<build><pluginManagement>` 把 surefire 固定为 **3.1.2**，所有模块统一
（`fact-check/pom.xml`）。实测 `mvn -o test` → 324 / 0 失败。

**若网络仍不稳**，用"只拷 jar"的离线镜像路线：

```powershell
cd fact-check && mvn -o clean package -DskipTests && cd ..
docker build -f fact-check/Dockerfile.server.local -t fact-check-server:latest ./fact-check
docker compose -f docker-compose.yml -f docker-compose.offline.yml up -d
```

### 11.5 Dockerfile 自检误判：`unzip: not found`

**症状**：用 `RUN unzip -l app.jar | grep -q 'BOOT-INF/'` 做自检，JRE 基础镜像里**没有 `unzip`**，
于是 `grep` 拿到空输入、判定"不是 Spring Boot 可执行 jar"而**构建失败** —— 但 jar 其实是好的。

**教训**：

- 自检命令依赖的工具必须确认基础镜像里存在；本机改用 JDK 自带的 **`jar tf`**。
- 更重要的：**自检不该成为构建的阻塞点**。现在写成"有 `jar` 就校验、没有就 SKIP"，
  唯一硬性判据是"jar 非空"。见 `fact-check/Dockerfile.server.local`。

### 11.6 ⚠️ 登录返回「未知错误」：JWT 密钥被注入成空字符串

**症状**：5 个容器全部 `healthy`，`/api/doc.html` 200，前端 200，管理端无 token 正确 401 ——
**但登录返回 `{"code":0,"msg":"未知错误"}`**。

**定位关键证据**：查库发现 `t_user.last_login_time` **已被更新为刚才那次登录的时间** ——
说明密码校验已通过、`userMapper.update()` 已成功，异常发生在**更靠后**的步骤。
而 `saveAdminLoginLog` 有 try/catch 兜底，所以只剩一处：**签发 token**。

**根因链**：

```
docker-compose.yml:  FACTCHECK_JWT_USER_SECRET: ${FACTCHECK_JWT_USER_SECRET:-}
                     └─ 变量未设置 → 注入"空字符串"
        ↓
application.yml:     user-secret-key: ${FACTCHECK_JWT_USER_SECRET:bb2db55...}
                     └─ 变量"已定义但为空" → 取空值，**不回落默认密钥**
        ↓
jjwt 0.12.5:         HS256 密钥必须 ≥256 位 → WeakKeyException
        ↓
UserServiceImpl:     token 签发抛异常 → 前端只看到「未知错误」
```

**为什么本机裸机跑没事**：那里变量**完全未设置**，Spring 会正确回落到默认密钥。
**只有 compose 这种"显式注入空串"的情形才会踩到。**

**已修（两处，互补）**：

| 位置 | 改动 |
| --- | --- |
| `docker-compose.yml` | `${VAR:-}` → **`${VAR:?中文提示}`**：未设置时 compose 直接报错并说明要设哪个变量（实测退出码 1 + 明确提示），把静默失败变成启动即失败 |
| `FactCheckApplication.java` | 新增 `validateJwtSecrets()`：启动时校验两个密钥 ≥32 字节，不足则启动失败并打印生成命令（实测 1 字节密钥 → `IllegalStateException` 退出） |

**正确的启动方式**：

```powershell
$env:FACTCHECK_JWT_USER_SECRET  = -join ((1..64) | ForEach-Object { '{0:x}' -f (Get-Random -Maximum 16) })
$env:FACTCHECK_JWT_ADMIN_SECRET = -join ((1..64) | ForEach-Object { '{0:x}' -f (Get-Random -Maximum 16) })
docker compose -f docker-compose.yml -f docker-compose.offline.yml up -d
```

> ⚠️ 环境变量在**容器创建时**注入，改完必须 `up -d` 重建容器才生效（只设 shell 变量没用）。

### 11.10 WebSocket 握手来源改为可配置

原实现硬编码 `setAllowedOrigins("*")`（任意站点都能发起握手）。现在由
`fact-check.websocket.allowed-origins` 驱动，默认仍是 `*` 以便本地开箱即用：

```bash
# 生产：改成真实前端域名（逗号分隔）
FACTCHECK_WS_ALLOWED_ORIGINS=https://factcheck.example.com,https://www.factcheck.example.com
```

**如何确认收窄生效**：看启动日志。

| 日志 | 含义 |
| --- | --- |
| `INFO ... WebSocket 允许的来源：[https://factcheck.example.com]` | ✅ 已收窄 |
| `WARN ... WebSocket 允许任意来源握手（... 含 "*"）` | ⚠️ 仍是 `*`，配置没生效或没设 |

**注意两个容易误解的点**：

1. **本项目不构成典型 CSWSH**：握手鉴权用的是**显式 token 查询参数**
   （`DetectWebSocketHandshakeInterceptor`），不是 cookie 自动携带，所以第三方页面拿不到你的凭据。
   收窄来源属于**纵深防御**——并能在将来鉴权方式改成 cookie 时提前拆掉这颗雷。
2. **Spring 不校验这个配置**：把键名写错（如漏掉 `websocket` 一层）会**静默保持默认的 `*`**，
   不会报错。所以必须以启动日志为准，而不是"我配了就行"。
