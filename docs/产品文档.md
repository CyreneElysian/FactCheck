## 1. 产品概述

### 1.1 背景
网络上的信息真伪难辨，普通用户缺少便捷的事实核查工具。本产品提供一套“AI 检测 + 人工兜底”的事实检测平台：
- 普通用户输入文字或上传图片，系统自动识别并给出“真 / 假 / 无法判定 / 待人工诊断”的结论和推理链。
- 当大语言模型无法判断时，转由管理员人工诊断。
- 管理员可以修改历史结论、处理用户申诉、发布权威信息。

### 1.2 产品定位
面向普通用户与管理员的事实核查 Web 应用 + 微信小程序。普通用户快速验证消息真假，管理员高效处理 AI 无法判定的问题并进行内容治理。

### 1.3 目标用户
| 用户 | 端 | 说明 |
| --- | --- | --- |
| 普通用户 | Web / 微信小程序 | 注册、登录，提交待检测消息，查看历史记录、热度榜、权威信息，发起申诉/纠错 |
| 管理员 | Web | 由管理员创建，处理待诊断消息、修改结论、处理申诉、发布权威信息、管理账号 |

### 1.4 核心价值
1. 对用户：输入即查，拿到结论和推理链，降低被谣言误导的风险。
2. 对管理员：AI 先过滤掉已有结论和可判断的问题，人工只处理疑难问题，效率更高。
3. 对平台：检测结果沉淀为知识库，相同/相似消息直接复用结论。

## 2. 名词定义

| 名词 | 说明 |
| --- | --- |
| 待检测消息（Claim） | 用户提交的一段文字，或图片 OCR 后得到的文字 |
| 检测记录（Record） | 一条消息的完整检测档案，包括内容、结论、推理链、证据、状态 |
| 结论（Verdict） | `真`、`假`、`无法判定`、`待人工` 之一 |
| 推理链（Reasoning Chain） | 结论的推理过程，分步骤说明判断依据 |
| 证据（Evidence） | 大模型联网搜索到或管理员补充的网页标题、链接、摘要、来源、相关度、来源可信度 |
| 权威信息（Authority Info） | 管理员发布的权威信息，用户可查看 |
| 申诉/纠错（Appeal） | 用户对某条检测结论提出异议，申请管理员复核 |
| 热度（Hot Score） | 基于检测次数、查看次数、申诉次数等计算的热度值，用于 Top10 榜单 |
| 小模型去重 | 用轻量模型判断“这条消息之前是否有人问过”，包括精确去重和语义相似去重 |
| 去重阈值 | 语义去重时判定“同一问题”的相似度分数线，默认 0.92，配置文件可调 |
| 站内信（Message） | 系统发给用户的站内通知，如申诉结果、人工诊断完成、结论被修改 |
| 微信绑定 | 微信小程序登录后，将微信 openid/unionid 与 Web 端 t_user 账号绑定，实现账号同步 |

## 4. 功能需求

### 4.1 账号模块

#### 4.1.1 用户注册
- Web 端用户打开注册页，填写：用户名、密码、确认密码、昵称（选填）。
- 用户名唯一，4-20 位，字母/数字/下划线。
- 密码 8-20 位，须包含字母和数字。
- 注册成功后跳转登录页。

#### 4.1.2 用户登录
- Web 端用户名 + 密码登录。
- 登录成功后返回 JWT 令牌和用户基本信息（ID、昵称、头像、角色）。
- 前端根据角色渲染用户界面或管理员界面。
- 密码错误、账号禁用/注销时给出明确提示。

#### 4.1.3 微信小程序登录与绑定（S11，方案 B）
- 小程序调用 `wx.login` 获取 code，后端通过微信接口换取 openid/unionid。
- 若 openid 已绑定 `t_user`：直接登录，返回 JWT，账号与 Web 端一致。
- 若 openid 未绑定：用户输入 Web 端账号密码完成一次绑定，后端将 openid/unionid 写入该用户记录。
- 之后打开小程序自动登录，无需再输密码。
- 同一用户的 Web 端和小程序端数据完全同步（同一张 t_user 表）。

#### 4.1.4 管理员账号
- 不提供公开的管理员注册入口。
- 管理员在“账号管理”中创建管理员账号：用户名、初始密码、昵称。
- 新建管理员首次登录建议强制修改初始密码（可选）。

#### 4.1.5 个人中心
- 右上角显示用户头像和昵称，点击进入个人中心。
- 可修改：昵称、头像、密码。
- 点击头像可上传新图片（存储到阿里云 OSS）。
- 修改密码需要输入原密码。
- 管理员拥有同样的个人中心。

#### 4.1.6 用户注销账号（S16）
- 用户可在个人中心申请注销账号。
- 注销后账号状态置为“已注销”，不可登录。
- 用户已提交的检测记录保留（事实结论需要保留），但展示时隐去用户个人标识。

### 4.2 事实检测模块

#### 4.2.1 提交方式
| 方式 | 说明 |
| --- | --- |
| 文字输入 | 文本框输入，限制 1-5000 字 |
| 图片上传 | 支持 jpg/png/webp，单张 ≤ 5MB；上传后存 OSS，调用 OCR 接口识别文字，识别结果可编辑后提交 |

#### 4.2.2 提交前检查
- **内容安全审核（S2）**：文字或图片在提交检测前进行内容安全审核；命中违法招揽类内容则拒绝提交并提示，命中敏感话题则放行并留痕（详见 §4.15）。
- **消息分类标签（S5）**：用户提交时可选择分类（健康、社会、财经、科技、政策、其他），默认“其他”。

#### 4.2.3 检测流程
1. 用户提交文字（或图片 OCR 后的文字）和分类标签。
2. 内容安全审核，不通过则拒绝。
3. 系统做内容规范化（去首尾空格、统一空白字符等），计算内容哈希。
4. 先查精确去重：MySQL 中是否已有相同 `content_hash` 的已完成记录。
   - 命中：直接返回历史结论和推理链，不创建新记录；记录本次命中日志并加热度。
5. 精确未命中，调用 Python 小模型语义去重（Embedding 相似度，阈值默认 0.92，配置文件可调）。
   - 相似度 ≥ 阈值：返回最相似的历史结论和推理链，标注“已存在相似问题”。
   - 相似度 < 阈值：继续下一步。
6. **权威信息联动（S19）**：查询已发布的权威信息，若消息与某条权威信息匹配（标题/关键词/语义匹配），在结果页优先展示权威信息入口和结论。
7. 创建检测记录，状态为“检测中”，交给 Python 大语言模型 Agent（可联网搜索）判断：
   - 能判断：保存结论、置信度、推理链、证据列表（含来源可信度 S13），状态为“已完成（AI 判定）”。
   - 不能判断：状态为“待人工诊断”，保存大模型搜索到的高相关度证据，交给管理员诊断。
8. 前端在提交后通过 WebSocket 实时接收结果，并以 2 秒轮询兜底（S18 已实现 WebSocket，见技术方案 §6.5/§9.3）。

#### 4.2.4 结果展示
- 结论徽章：真（绿）、假（红）、无法判定（灰）、待人工（橙）。
- 展示推理链（分步骤）。
- 展示证据列表：标题、来源、摘要、链接、相关度、**来源可信度**。
- 若命中权威信息，优先展示权威信息卡片。
- 若为“待人工诊断”，提示用户“该消息已进入人工诊断队列，请稍后查看”。
- 结果页提供“申诉/纠错”、“收藏”、“分享”、“有帮助/无帮助”入口。

### 4.3 历史记录模块
- 用户可查看自己提交过的全部检测记录，分页展示。
- 列表字段：内容摘要、分类、提交方式（文字/图片）、结论、状态、提交时间。
- 支持按状态/结论/分类/时间范围筛选。
- 点击进入详情，查看完整内容、图片、OCR 文本、推理链、证据、结论。
- 详情页可：收藏/取消收藏、生成分享卡片、对结果评分、发起申诉。

### 4.4 热门消息 Top10
- 展示最近热门消息 Top10：内容摘要、分类、结论、热度值、被检测次数。
- 点击进入详情查看完整推理链和证据。
- 热度计算规则见《技术方案》Redis 设计。
- 防刷：同一用户对同一消息短时间内只计一次热度。

### 4.5 申诉/纠错模块
- 用户在检测记录详情页点击“申诉/纠错”。
- 填写：申诉类型（结论错误、证据不足、来源不可信、其他）、申诉说明（≤ 500 字）。
- 提交后管理员可见。
- 管理员处理结果：采纳（修改结论并附原因）或驳回（填写驳回原因）。
- 用户可在申诉记录中查看处理结果，并通过站内信收到处理通知（S7）。

### 4.6 权威信息模块
- 管理员发布权威信息：标题、正文、分类、来源、原文链接、封面图（可选）。
- 用户端可查看权威信息列表和详情，支持按分类筛选和关键词搜索。
- 状态：草稿、已发布、已下线。
- 检测时如与权威信息匹配，结果页优先展示权威信息（S19）。

### 4.7 管理员 - 待诊断热门消息 Top10
- 展示待诊断消息 Top10，按“请求诊断次数/热度”排序。
- 列表字段：消息内容摘要、分类、请求诊断次数、最早/最近请求时间、AI 置信度、证据数量、**是否超时**。
- 点击进入“诊断工作台”。

#### 4.7.1 诊断工作台
- 展示：消息完整内容、分类、用户上传的图片、OCR 文本、大模型搜索到的证据列表（按相关度降序，含来源可信度）。
- 管理员可：
  - 判定结论：真 / 假 / 无法判定。
  - 填写结论说明/推理依据（必填）。
  - 采纳、补充或删除证据。
  - 将该结论发布为权威信息（可选）。
- 提交后，该记录状态变为“已完成（人工判定）”，用户下次查看时可见结果，并通过站内信通知用户（S7）。

#### 4.7.2 超时提醒与转派（S14）
- 待诊断记录默认处理时限 48 小时，**可通过 `fact-check.pending.timeout-hours` 调整**
  （环境变量 `FACTCHECK_PENDING_TIMEOUT_HOURS`；下限 1 小时，配 0 或负数会被归一化并打 WARN）。
  记录进入待诊断队列时写入 `deadline = 当前时间 + 该时限`。
- 超时未处理的记录在待诊断 Top10 中高亮“已超时”。
- 管理员可将待诊断记录转派给其他管理员（记录当前处理人）。
- 超时和转派均写入操作日志（S3）。

> **实现变更留档**：该时限原先是硬编码常量（`DetectServiceImpl.PENDING_HOURS = 48`），
> 本文档却写成“配置项可调”——**文档承诺了一个实际不存在的能力**，部署方按文档去改配置
> 会发现无处可改且无任何报错。2026-10-05 已提为配置项（`PendingProperties`）。

### 4.8 管理员 - 结论管理
- 查询全部检测记录，按状态/结论/分类/时间筛选。
- 查看任意记录详情。
- 修改历史结论并附原因（必填），保存修改版本记录，可追溯。
- 修改后记录版本号 +1，用户查看时展示最新结论和修改原因（可查看历史版本），并通过站内信通知相关用户（S7）。

### 4.9 管理员 - 权威信息管理
- 新增、编辑、下线、删除权威信息。
- 管理分类（内置固定分类即可）。

### 4.10 管理员 - 账号管理
- 创建管理员账号。
- 查询用户列表，启用/禁用用户。
- 重置用户密码（可选）。

### 4.11 管理员 - 统计与日志（S3、S8）
- 工作台统计：今日检测量、AI 判定**数**、人工诊断数、待诊断数、申诉待处理数、注册用户数。
  （口径为**计数**而非比率 —— 与 §9 验收标准的措辞一致）
- 操作日志：记录管理员关键操作（登录、诊断、修改结论、发布信息、创建账号、转派等），可查询。

### 4.12 站内信模块（S7）
- 系统自动发送站内信通知用户：
  - 检测结果已出（AI 判定完成）
  - 消息已进入人工诊断队列
  - 人工诊断完成
  - 申诉处理完成
  - 历史结论被修改
- 用户右上角/小程序“我的”中有未读消息红点。
- 用户可查看站内信列表和详情，标记已读。

### 4.13 收藏与分享（S12）
- 用户可收藏检测结果，在个人中心查看收藏列表。
- 分享：前端生成分享卡片图片（消息摘要 + 结论 + **记录链接** + 平台标识），下载后由用户自行发给他人。
- 小程序端分享：使用微信原生分享卡片（标题为消息摘要，路径带 `recordId`，进入后需登录）。
- **分享卡片不生成二维码（已决策，非未完成项）**。理由：
  1. 记录详情**仅归属者可见**（越权保护），扫二维码的人打开看到的仍是登录页——与直接收到链接相比没有增量价值；
  2. 小程序端已有体验更好的微信原生分享（卡片直接进聊天），二维码更适合线下物料，而本项目没有线下投放场景；
  3. 生成二维码需要引入编码实现（npm `qrcode` 或 Maven zxing），属于"为低价值功能增加依赖与维护面"。
  若将来确有线下投放需求，补做方案见 [`决策-分享卡片不生成二维码.md`](决策-分享卡片不生成二维码.md)（含可自动化验证的往返测试）。
- **隐私边界**：分享本身不开放"按 ID 查询任意记录"的接口。唯一公开的读取入口是热度榜详情
  （`GET /hot/{recordId}`），且**仅放行当前在 Top10 内的记录**、返回脱敏视图——详见技术方案 §10 的"公开视图边界"。

### 4.14 检测结果评分（S6）
- 用户可对检测结果点“有帮助”或“无帮助”。
- 评分结果用于后续模型优化和运营分析。
- 同一用户对同一记录只保留一次评分，可修改。

### 4.15 内容安全审核（S2）
- 文字检测：提交前进行内容安全审核。
- 图片检测：图片提交时一并审核图片地址。
- **分级处置**：
  - 命中明确的**违法招揽类**内容（色情招嫖、赌博推广、诈骗引流、违禁品交易，且带联系方式）→ 拒绝提交，提示“内容涉嫌违规，请修改后重试”；
  - 命中**敏感话题**（疫情、恐怖袭击、自杀等）→ **放行**并记录审核日志。原因：本平台用户提交的正是待核查的说法，其中天然包含这类词（例如“武汉又出现新型病毒了，大家不要出门”），一律拦截会直接挡掉核心场景。
- 审核结果记录到审核日志，便于排查。

> 实现说明：当前默认使用**本地确定性规则**（`local`），已预留可插拔接口，接入云端内容安全服务只需实现 `ContentSafetyChecker` 并切换 `fact-check.content-safety.provider`，业务代码无需改动。
> 能力边界：本地规则无法识别图片内容本身，也无法识别谐音、拆字、拼音等变体；图片审核目前只校验地址（协议、主机名、可选域名白名单）。

## 5. 核心业务流程

### 5.1 检测主流程（文字/图片）
```
用户提交文字/图片OCR文字 + 分类标签
    │
    ▼
内容安全审核（本地规则，可切换云端）
    │命中违法招揽类
    ├──────────────► 拒绝提交并提示
    │通过 / 命中敏感话题（放行但记日志）
    ▼

    │
    ▼
MySQL 精确去重（content_hash 已存在且已完成？）
    │命中
    ├──────────────► 返回历史结论 + 推理链，记录命中日志，热度 +1
    │未命中
    ▼
Python 小模型语义去重（Embedding 余弦相似度，阈值默认 0.92）
    │相似度 ≥ 阈值
    ├──────────────► 返回最相似历史记录结论 + 推理链，记录命中日志，热度 +1
    │相似度 < 阈值
    ▼

    ▼

    │
```

### 5.6 微信小程序登录绑定流程（S11）
```
小程序 wx.login 获取 code
    │
    ▼
后端调用微信接口换 openid/unionid
    │
    ├─ openid 已绑定 t_user ──► 直接登录，返回 JWT（账号与 Web 同步）
    │
    └─ openid 未绑定 ──► **由用户选择一条路**（不再强制绑定）
                          │
                          ├─ ① 创建新账号：填用户名/密码/昵称
                          │     后端在**同一事务**里完成「注册 + 绑定微信」，
                          │     直接返回 JWT（省掉一次登录往返）
                          │
                          └─ ② 绑定已有 Web 账号：填 Web 端用户名/密码
                                校验通过后写入 openid/unionid，返回 JWT
```

> **实现变更留档（2026-10-05）**：原先 `openid 未绑定` 只有**一条路** —— 强制输入
> Web 端已有的账号密码去绑定。没有 Web 账号的**新用户被完全挡住**，
> 而本文档 S11 的描述也只写了"绑定 Web 账号"，等于把"新用户无法注册"这个缺口
> 写成了设计。现已改为二选一：**创建新账号** 或 **绑定已有账号**。
>
> 两个实现要点：
> * 小程序端注册走 `POST /user/register` 并带上 `code`，后端在**同一事务**里
>   完成注册 + 绑定。分两步做的话，绑定失败会留下"账号已建但没绑微信"的中间态 ——
>   用户不知道注册成功了，再试一次撞"用户名已存在"，用微信登录也仍然进不去；
> * 小程序端注册与 Web 注册**共用同一套校验**（用户名唯一性、密码强度规则
>   `ValidationUtils.requireStrongPassword`）与**同一套注册限流**，
>   避免小程序端成为绕过弱口令校验或注册限流的旁路。

> **范围决定（2026-10-05）**：管理端共 8 个控制器、约 25 个接口，
> 小程序端**只搬手机上真正用得上的三块** —— 待诊断（管理员的日常工作，适合随时处理）、
> 申诉处理（表单轻）、统计概览（只读、成本低）。
> **刻意不搬**：结论管理（重表单 + 需填修订原因）、权威信息 CRUD（长文本录入）、
> 账号管理 / 操作日志（低频敏感操作）—— 这些在 PC 端做更合适。
>
> **两条实现约束**：
> 1. 角色判断放在**「我的」页 `onShow`**，而不是"登录时"。冷启动复用缓存 token 时
>    走的是 `app.onLaunch` 的"直接复用"分支，**根本不经过登录流程**，
>    只在登录时分支会被跳过 → 管理员看到用户界面。`role` 已持久化在 storage，`onShow` 读取零成本。
> 2. 管理页面必须有 **`ensureAdmin()` 守卫**（小程序没有 Web 那样的路由中间件）。
>    ⚠️ 客户端只是 **UX 层**：真正的权限判定在**后端 `JwtTokenAdminInterceptor`**，
>    隐藏入口不能当作安全边界。
>
> **提交体字段以前端读到的后端 DTO 为准**：`AdminConclusionDTO` 只有
> `verdict` / `reasoningChain` / `reason`；`AdminAppealHandleDTO` 只有
> `accept` / `handleResult` / `newVerdict` / `newReasoningChain`。
> 多传的字段会被**静默忽略**，因此前端不做后端不支持的"就地编辑"功能
> （那会给出一个看起来能用、实际无效的假功能）。

## 9. 验收标准（摘要）

1. 普通用户可注册、登录、修改资料和密码、更换头像、注销账号。
2. 管理员只能由管理员创建，管理员登录后进入管理端界面。
3. 文字检测全流程可用：内容安全审核 → 分类选择 → 去重 → AI 判断/转人工 → 结果与推理链展示。
4. 图片检测全流程可用：上传 → OSS → 内容安全审核 → OCR → 可编辑文字 → 检测。
5. 历史记录、热度榜 Top10、权威信息查看可用。
6. 申诉/纠错全流程可用，处理结果通过站内信通知。
7. 管理员可查看待诊断 Top10（超时高亮），人工诊断、转派并填写依据。
8. 管理员可修改历史结论并附原因，修改记录可追溯。
9. 热度榜使用 Redis 计算并每日衰减。
10. 去重开关（`exact-enabled` / `semantic-enabled`）、最短文本长度（`min-text-length`）、
    语义相似度阈值均可在配置文件中调整。
    ⚠️ **两个配置位置不要搞混**：
    * Java 侧 `fact-check.agent.semantic-threshold` 是**占位配置，改了不生效也不会有任何告警**
      （保留它只是为了与配置清单一致）；
    * 语义去重阈值的**真正生效点**是 Python Agent 的 `DEDUP_THRESHOLD`
      （`fact-agent/.env`，默认 0.92）。其余三项在 Java 侧 `fact-check.agent` 下，真正生效。
11. 微信小程序可用：微信一键登录，未绑定用户可绑定 Web 账号，数据与 Web 端同步。
12. 用户可收藏、分享、评分检测结果；证据列表展示来源可信度。
13. 检测命中权威信息时结果页优先展示权威信息。
14. Java 代码有 Javadoc 注释和 SLF4J 日志；前端部署在 nginx-1.20.2/html/fact-check。
15. 待诊断记录处理时限可配置（`fact-check.pending.timeout-hours`，默认 48 小时）。
16. 检测结果通过 WebSocket 实时推送，前端以轮询兜底。
